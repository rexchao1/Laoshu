# Checkpoint 8 decisions: Write a plain meaning for every word

Every card's English now reads as a plain usable meaning. Where the user once saw "the Great Learning, one of the Four Books 四書|四书[Si4 shu1] in Confucianism" for 大学, or "erhua variant of 好玩[hao3 wan2]" for 好玩儿, or "to touch briefly; to tap" for 点 whose HSK 1 uses are o'clock and "a bit", the card, the browse row, the session summary's parked words, the placement result's known words, and the reverse direction's prompt all now show a short gloss written for a learner: "university", "fun; amusing", "o'clock; a little". Nothing about scheduling, swiping or the session changed.

One line per decision: what was decided, and the citation from the frozen plan, copied rather than paraphrased.

D1. All 5,400 words get a gloss, not a subset. Cited: route line 8, "every card's English reads as a plain usable meaning". A gloss set that covers only the levels studied so far would leave the defect live for every level the user has not reached, and the cost of the remaining levels is the same batch either way.

D2. A gloss is one meaning, in English, in at most 40 characters, with a second sense only where a learner meets the word both ways. The 40 is measured, not borrowed: the cleaned CC-CEDICT definitions run 22 characters at the median and 45 at the ninetieth percentile, and 4,600 of the 5,400 already fit in 40, so the cap tightens the tail rather than forcing a rewrite of the whole set, and it holds a card's meaning face to two lines at the 26pt the card renders. It is not `CatalogueBuilder`'s 60, which is the threshold at which the cleanup drops from two senses to one, nor its 90, which is where that rule truncates; borrowing either would tie this decision to a rule it is replacing (critique round 1 finding F7). Cited: Laufer and Shmueli 1997, System 25(1); Yanagisawa, Webb and Uchihara 2020, Studies in Second Language Acquisition 42(2). The evidence is not one-sided: the same meta-analysis found multiple-choice glosses beat single ones. What settles it here is that the app grades the user's own recall of one word, so a card offering alternatives would grade something else.

D3. The glosses are a committed data file, `data/glosses.tsv`, with `word_index` and `gloss` columns, one row per word. `laoshu-build-db` takes it as a required third positional argument, so the build command becomes `laoshu-build-db data/hsk_word_list.tsv data/glosses.tsv data/laoshu.sqlite`. Two files carry the old two-argument form and both are updated by this checkpoint: `README.md`, which is where a person is told how to rebuild the catalogue, and `docs/decisions/checkpoint-01.md`, the one record that carries it. Checkpoints 2, 3, 4 and 11 carry only the `--checksum` form, which this does not change (critique round 4 finding F4). That is the point: an optional argument or a default path would let a build silently produce a catalogue with no glosses, and a required one cannot. The closure task records the new command and says which records it supersedes. A flag would do the same job, and a positional is chosen only because the tool's argument handling is a switch on argument count with no parser to extend (critique round 2 finding F5). Nothing calls a model at build time. Cited: checkpoint 1 D14 makes the catalogue rebuild deterministic, proved by a SHA-256 the decision records carry; a build that asks a model for text is not reproducible and would break that check on every run. Committing the glosses also makes them reviewable in a diff, which is the only way a wrong gloss gets caught before it is studied.

D4. Nothing is renamed. The `word` table's `definition` column keeps the cleaned CC-CEDICT text exactly as it holds it today, and a new `gloss TEXT NOT NULL` column carries the gloss. `Word.definition` keeps its current meaning and a new `Word.gloss` property reads the new column, Two queries build a `Word` and both list their columns explicitly, `Word.fetch` at `LaoshuKit/Sources/LaoshuKit/Word.swift` and `SessionEngine.browse` at `LaoshuKit/Sources/LaoshuKit/SessionEngine.swift`, and both gain the column. The browse query is the one D4a names as a surface that must show the gloss, so `Word.init(row:)` reading a `gloss` that query did not select would be the browse screen failing on a change this decision calls harmless (critique round 3 finding F5). A rename would break `laoshu-build-db`'s insert, `Word.init(row:)`, `SessionEngine.browse`, and checkpoint 11 D10's recorded agreement command `sqlite3 -tabs data/laoshu.sqlite 'select word_index, definition from word order by word_index'`, which would silently start comparing a gloss against the Python `clean()` output. Adding a column breaks none of them, and that command stays in this checkpoint's Acceptance checks unchanged as the proof (critique round 1 finding F1).

D4a. Five places on screen show a word's meaning, and every one of them shows the gloss: the card's meaning face at `Laoshu/CardView.swift`, which is the back in the receptive direction and the front in the reverse one; the browse row at `Laoshu/LevelBrowseView.swift`; the end-of-session summary's parked words at `Laoshu/SessionSummaryView.swift`, under checkpoint 1 D27; and the placement result screen's list of words marked known at `Laoshu/PlacementResultView.swift`, under checkpoint 3 D17a. The placement result is in rather than out, unlike checkpoint 11 D13's holding placement out of the direction: a direction is a way of asking, and a placement card asks nothing on its back, while a gloss is just the English for a word, and the screen listing what the user said they knew is a screen listing meanings. `Laoshu/PlacementCardView.swift` stays untouched because it shows no meaning at all. The summary screen matters most of the five: it lists the words the user just failed three times, which are the words whose English they most need to be able to read (critique round 1 finding F2). Cited: keeping both is what lets the acceptance checks diff a gloss against the source it came from, and what makes a bad gloss recoverable by editing one file rather than regenerating the set.

D4b. Two words may share a gloss, and this is accepted rather than prevented, but it is measured before it is accepted. D2 replaces a two-sense definition with one short meaning, which can only raise collisions, and in the reverse direction a gloss is the prompt, so this directly weakens what checkpoint 11 D9 and D9a rest on: 274 of 5,400 words sharing a cleaned definition catalogue-wide and 89 sharing one inside their own level. What carries a shared prompt is unchanged and is the user's own grade, per the review answer of 2026-09-08, "If I know it I will say I know it". What must not happen is checkpoint 11's decisions being left citing a string the app no longer shows. So `docs/measure.py` gains a gloss pair of columns in the "Definition and pinyin collisions by level" table checkpoint 11 D10 built, counting gloss collisions catalogue-wide and inside the level exactly as it counts definition collisions, `docs/measurements.md` is regenerated, and the closure task records the new numbers and amends checkpoint 11 D9 and D9a to cite them.

D4c. `docs/measure.py` also emits and asserts the numbers D2 and D5 rest on, which are today recorded nowhere the repository can regenerate: the count of cleaned definitions at or under 40 characters, 4,600 of 5,400, and the eight mechanical-signal counts, 293 flagged by any signal with 34 at level 1, of which 83 carry bracketed pinyin, 73 hanzi, 66 "surname", 45 "(bound form)", 37 "variant of", 32 a trailing "...", and 59 the word's own hanzi. Cited: checkpoint 11 D10 established that a number a decision rests on is generated and asserted by the script so a later change that moves it fails the diff, and this checkpoint is already editing that script (critique round 4 finding F5). The generation pass is given no distinguishability rule: a rule that forced two genuinely synonymous words apart would produce a gloss written to be different rather than to be true, which is a worse fault than a shared prompt (critique round 1 finding F3).

D5a. The banned list is patterns, not bare words, because two of the tags are also real English meanings. `surname` appears 66 times in the shipped definitions: 61 as CC-CEDICT's tag, always `surname` followed by a capitalised Latin name, and 5 as an actual meaning, of which 姓 at `word_index` 464 is the clearest, cleaning to "family name; surname; to be surnamed ..." where surname is the whole word. So the validator bans `surname` followed by a capitalised word, not the word itself, and 姓 may be glossed "surname; family name". `variant of`, `old variant of`, `erhua variant of`, `abbr. for` and `(bound form)` are banned outright, since none of them is ever the meaning of an HSK word. Hanzi, a bracketed pinyin reference, and a trailing `...` are banned outright too. Measured on 2026-09-09 over `data/laoshu.sqlite` (critique round 3 finding F1).

D5. The deterministic cleanup rule stays and runs first, but it is not what fixes this. Cited: measured on 2026-09-09 over the shipped catalogue. Eight mechanical signals flag 293 of 5,400 definitions, 5.4 per cent, and 34 of level 1's 300: 83 carry bracketed pinyin, 73 carry hanzi, 66 say "surname", 45 say "(bound form)", 37 say "variant of", 32 end truncated. A hand review of level 1's first 100 words on the same day found 6 whose card gives the wrong meaning or no meaning, and the clearest of them, 点 reading "to touch briefly; to tap", trips none of the eight signals. So no regex over CC-CEDICT decides which words need rewriting, and 293 is a floor on the job rather than its size.

D6. The glosses are written by a batch model pass and verified by a second, independent pass before anything is committed. Both passes see the collapsed row, the one checkpoint 1 D15 keeps at the word's lowest level, and read `word_index`, `level`, `part_of_speech` and the raw CC-CEDICT entry from it. 81 `word_index` values appear on more than one source row with different levels and parts of speech, so which row feeds the pass has to be said: 点 at `word_index` 33 is level 1 as 量 and level 3 as 名, and only the level-1 量 row makes "o'clock" the right gloss, which is what the six-word check asserts (critique round 3 finding F3). Both passes see and the second also sees the proposed gloss and answers only whether it names a real and primary meaning of that word at that level. `part_of_speech` is in that list because it is the only field that separates some rows. Measured on 2026-09-09 over `data/hsk_word_list.tsv`: 61 shipped words carry a trailing digit, as `docs/measurements.md` records, and those 61 reduce to 36 distinct base hanzi once checkpoint 1 D9 strips the suffix. 20 of those 36 base hanzi ship at two or more levels, as two or more distinct `word_index` values with byte-identical CC-CEDICT entries; no single word ships twice, since checkpoint 1 D15 collapses each `word_index` to its lowest level. 本 is `word_index` 10 at level 1 as 量 and `word_index` 2040 at level 5 as 副、代 (critique round 3 finding F6). Checkpoint 1 D9 strips the suffix for display and `part_of_speech` is the one field the catalogue drops, so without it the generation pass would see two identical inputs whose right glosses differ, and D2's "the meaning a learner meets" would have nothing to read it from (critique round 2 finding F6). Every disagreement goes to a list, and the planning agent reads every entry on it in this session, not the user: reading a rejected gloss beside its raw CC-CEDICT entry is the same judgement the generation pass just made, and the user's read of the glosses is the app itself. A rejected gloss is rewritten once by hand, in this session, from the raw entry, and the hand-written gloss must pass the validator like any other. There is no fallback to the cleaned CC-CEDICT definition: those run to 90 characters and 293 of them carry exactly the substrings the validator bans, so a fallback would fail the build rather than ship, and every HSK word has some short English rendering. The count the decision record carries is the number of hand-written glosses, which is the honest measure of where the passes could not be trusted (critique round 3 finding F1). If the list runs past 540 entries, ten per cent, the generation prompt is wrong rather than the glosses, and the fix is to correct the prompt and regenerate rather than to read 540 items. Two passes agreeing on a wrong gloss produces no list entry at all, which is the hole in this design, so a stratified random sample of 100 agreed glosses, spread across the six levels, is also read in full, and any error found there is treated the same way a size overrun is: fix the prompt, regenerate (critique round 1 finding F5).

D6b. Twelve shipped words carry a CC-CEDICT entry with no English in it at all, only a cross-reference: 好玩儿 `word_index` 75, 面条儿 127, 一点儿 261, 小孩儿 461, 聊天儿 756, 一块儿 924, 差点儿 1070, 干活儿 1234, 体检 1732, 纪录 2542, 大伙儿 3850 and 下功夫 5014. Eleven are erhua or orthographic variants and one, 体检, is an abbreviation. D6's inputs cannot produce a gloss for them and give the verification pass nothing to check against, and D5a bans the very pattern their entry consists of. Their glosses are written by hand in the planning session, from the meaning of the referenced word, and are marked as hand-written in `docs/gloss-review.md` so the verification pass judges them on meaning alone rather than against a source string. Twelve is small enough to name in full, which is why they are named here rather than left to a rule. Measured on 2026-09-09 over `data/hsk_word_list.tsv` after checkpoint 1 D15's collapse (critique round 4 finding F1).

D6a. Both reviews are committed, at `docs/gloss-review.md`: every disagreement with the verdict and what was done about it, the 100 sampled glosses with a pass or fail against each, and the count of words that fell back to their cleaned CC-CEDICT definition. Without this the checkpoint goes green whether the review was done well, badly, or not at all, since the review happens in the planning session and leaves nothing a check can read. The closure task records the three counts from that file, and the number of fallbacks is the honest measure of how much of route line 8 this checkpoint actually delivered (critique round 2 finding F7). Cited: arXiv 2311.06362, where GPT-4 captured the primary sense on 48 of the 50 hardest cases against Merriam-Webster; and arXiv 2410.03182, which reports hallucination rising in cross-lingual settings. No published protocol exists for a batch of this size.

D6c. The planning session validates `data/glosses.tsv` against D2 and D5a before committing it, with a script committed at `docs/check_glosses.py` that applies the same rules the Swift validator will: not empty, at most 40 characters, no banned pattern, one row per built word, no duplicate `word_index`. It runs against the built word set derived from `data/hsk_word_list.tsv` the way `docs/measure.py` derives it, so it needs no database and no Swift. This exists because D7 puts generation in the planning session while D3a puts the validator in code a factory task writes, so without it nothing checks the file at the moment it is written and the first real build would reject an unknown number of glosses. A factory task whose build is rejected by the validator stops and says which `word_index` failed. It does not hand-edit glosses and it does not relax the cap: regenerating and hand-rewriting are planning-session work under D7 (critique round 4 finding F3).

D7. The generation and verification passes run in this planning session, not in the factory, and the committed `data/glosses.tsv` is their output. Cited: the light factory's own rule that a pebble built outside the factory is recorded with `planning-set-pebble-built`. A factory task cannot hold 5,400 generated lines in one pull request body or one worker context, and splitting generation across levels would push this checkpoint past the five-task limit on its own. Subagents do the writing, one per block of words, each writing its block to a file and returning only a count, so no gloss text passes through the planning conversation.

D7a. One task regenerates and commits `data/laoshu.sqlite` by running `laoshu-build-db data/hsk_word_list.tsv data/glosses.tsv data/laoshu.sqlite`, and it is the same task that adds the `gloss` column, the validator and the third argument. It lands no later than the pull request adding `Word.gloss` and the two queries, because `Word.init(row:)` reads columns by name and both queries list them explicitly, so code reading a `gloss` against the still-committed six-column catalogue fails on "no such column" at every draw and every browse, and none of D4a's screenshots could be taken. The Acceptance checks presuppose this has happened: the first checksum is over the committed database (critique round 4 finding F2).

D8. No new data source. Cited: nothing openly licensed beats CC-CEDICT on coverage. Every full-coverage HSK 3.0 dataset found is a CC-CEDICT wrapper and inherits the same multi-sense glosses, including `drkameleon/complete-hsk-vocabulary` and the `Punpuf/hsk-syllabus-vocabulary-parser` this repository already vendors; the official CLEC syllabus carries no English at all; Unihan glosses single characters, not words; SUBTLEX-CH offers one frequent translation per word but states only a citation request rather than a licence and is not confirmed against the 5,400-word list.

D9. No existing parser is adopted. Cited: `cedict_utils`, `hermanschaaf/cedict`, `jcramb/cedict` and `edvardsr/cc-cedict` all split the raw line on `/` and pass every convention through untouched, and Pleco shows the tags raw. The one stripping rule found in the wild, `rubber-duck-dragon`'s `remove_surnames()`, only deduplicates surname senses. The conventions themselves are documented at `cc-cedict.org/wiki/syntax`.

D10. The glosses are Adapted Material under CC BY-SA 4.0 and this changes nothing while the app stays personal. Cited: the licence gates both attribution and ShareAlike on Share, defined as making material available to the public, and Creative Commons' own ShareAlike interpretation states an unpublished adaptation triggers neither. The route's Not on the route list rules out App Store release, TestFlight and other users. `data/ATTRIBUTION.md` gains a paragraph saying the glosses are adapted from CC-CEDICT and that sharing the app or the data with anyone would activate both conditions, so the fact is recorded where it would be needed rather than rediscovered.

D11. `gloss` joins the checksum projection, and the checksum therefore changes. It would not change on its own: `readChecksumRows` hashes a fixed six-column projection of `word_index`, `level`, `hanzi`, `pinyin`, `pinyin_numbered` and `definition`, so adding a column and 5,400 values leaves the SHA-256 at `c4a5f6c2d416185e1f7f3bc071268cfa282ae78d66ddb834e5fb91c413f360a5` and a build that dropped every gloss would check out identical (critique round 2 finding F2). Cited: checkpoint 1 D14 exists to prove a rebuild is deterministic, and after this checkpoint the gloss is part of what a rebuild produces, so a checksum blind to it proves less than it did. The projection gains a seventh column and the row string gains a seventh tab-separated field. The proof that the definitions did not move is not the checksum and does not need to be: it is checkpoint 11 D10's `--dump-definitions` diff, already in the Acceptance checks, which compares all 5,400 definitions field by field and is strictly stronger than a hash that changed for an unrelated reason. The closure task records the new checksum and says it supersedes the value carried by all five earlier records, `docs/decisions/checkpoint-01.md`, `-02`, `-03`, `-04` and `-11`, the most recent of which is checkpoint 11's rather than checkpoint 4's. It also records that checkpoint 11 D6a's "the meaning face, which is the definition alone" is amended by D4a: the meaning face is the gloss alone.

D12. No new package dependency. Cited: checkpoint 2 D23.

D13. Nothing about the session changes. No scheduling, no swipe, no batch, no direction. Cited: this checkpoint changes one string per word and the column it lives in.

## Two findings, both already on main

These were found while verifying the earlier tasks of this checkpoint, not acted on here.

**Glosses collide more than definitions, and at level 1 more than pinyin.** The regenerated table shows 511 words sharing a gloss with another word catalogue-wide against 274 sharing a definition, and 162 inside their own level against 89. This was expected, because replacing a two-sense definition with one short meaning can only raise collisions. What was not expected is that at level 1 the gloss now collides more often than the pinyin does, 22 within-level against 16, which reverses the comparison checkpoint 11 D9 and D9a were decided on. What carries a shared prompt is unchanged: the user's own grade, per the review answer of 2026-09-08.

**The plan's count of mechanically flagged definitions does not reproduce, and the plan is what is wrong.** Decision D5 says eight mechanical signals flag 293 of 5,400 definitions with 34 at level 1, and decision D4c repeats it. The plan only ever names seven of those eight signals. The union of the seven it names is 214, with 26 at level 1, and every individual signal count reproduces exactly: 83 bracketed pinyin, 73 hanzi, 45 "(bound form)", 37 "variant of", 32 trailing ellipsis, 59 the word's own hanzi. Identical individual counts with a smaller union is what shows the patterns are the same and the recorded total was simply wrong; the eighth signal is named nowhere and cannot be reproduced. 214 and 26 are the numbers `docs/measure.py` now asserts; they supersede D5's and D4c's 293 and 34 for that reason. Separately, the surname signal counts 61 rather than the plan's 66 because it matches the tag form, "surname" followed by a capitalised name, rather than the bare word, which is what D5a's own banned-pattern rule requires. None of this changes D5's conclusion, which is that no mechanical rule decides which words need rewriting.

## Not run here

The screenshots the plan names were taken by the tasks that built those screens, and by the planning session; this task does not retake them. The user runs these on the phone, since they need a physical device and eyes on it:

1. Open a session at whichever level you are studying and read the English on the first three cards it draws. For each, say whether it is a meaning you could actually use, and name any that is not.
2. Open browse for a level you have studied and read down the meanings. Name any row whose English you would not be able to answer from.
3. Turn the direction round, read three fronts, and say for each whether you could tell which Chinese word is being asked for.
4. Left-swipe a card three times to park it, finish the session, and say whether the parked word's meaning on the summary screen tells you what you got wrong.

Anything named in steps 1 to 4 is one line to change in `data/glosses.tsv`, and is an amendment on the route rather than a defect in this checkpoint.
